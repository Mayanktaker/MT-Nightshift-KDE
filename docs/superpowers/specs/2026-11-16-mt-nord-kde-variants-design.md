# MT Nord KDE — Night and Day variants

## Intent and why

Add a canonical Nord identity to this KDE theme set in both directions, alongside
Nightshift and Dayshift. The user wants recognisable Nord (Polar Night / Snow Storm /
Frost / Aurora), not a rehash of the MT Nordic Blue GNOME palette: two Nord identities
on one machine would be confusing. Geometry, interaction states and the Qt style stay
identical to the existing pair — only the palette changes.

## Goals

- Two full variants, each with a color scheme, Plasma Style, Look-and-Feel package and
  Aurorae decoration, with unique ids and metadata.
- Every palette copy byte-identical to its scheme; both Nord schemes pass the same
  4.66:1 text / 3:1 non-text audit as the existing pair.
- All four variants stay under one generator drift check, one audit and one apply /
  verify-live path. No new C++ plugin and no new SVG geometry.
- Fix the two latent shared-generator defects the review found (button state colours
  and frame-line derivation) for all four variants, so no variant ships near-invisible
  titlebar icons or a frame line that disagrees with its own palette.

## Non-goals

- No changes to existing palette *values*, package ids, or the shared plugin key.
- Dayshift decoration artwork may be regenerated by the approved generator fix; its
  scheme values and package metadata stay untouched.
- No cursor, icon, wallpaper or GNOME-side work.
- No new Qt plugin: the existing `MTNightshift` plugin is palette-driven and shared.

## Anti-goals

- Reusing MT Nordic Blue values or baking Nord tones into shared geometry generators.
- Hand-editing generated SVGs or duplicating whole package trees as the maintenance
  model.

## Constraints

- `tools/decoration-probe/build-decoration.py --check` compares committed artwork with
  the generator for every registered variant; Nord artwork must be generated, not drawn.
- `tools/theme-audit/check-theme.py` requires **one version across all registered
  packages** and derives ids/copy identity from a variant table. All Nord packages
  therefore ship at the current shared version, **1.6.0**, not 1.0.0.
- `check-style.py --light` currently asserts palette-agnostic invariants on light
  renders, but its dark assertions hardcode Nightshift's Window tone and near-white
  pill text. Four-scheme verification requires per-variant reference tones, not just a
  flag.
- `make check` and CI must pass for all four variants; live state is checked by
  `make verify-live` against the selected variant.

## Approaches

- **A. Data-driven variants (chosen).** Register `nord-night` / `nord-day` in the two
  existing variant tables, author the schemes and package folders, and generalise the
  Makefile's binary `DAYSHIFT` switch into a named variant table. Touches shared tooling
  but duplicates no geometry and keeps every variant under the same checks.
- **B. Copy and hand-retint.** Clone the existing folders and renumber colours. Breaks
  generator drift checks and forks maintenance. Rejected.
- **C. Two colour schemes only.** No Nord decoration or Look-and-Feel identity. Fails
  full parity. Rejected.

## Design

### Naming

| Item | Night | Day |
|---|---|---|
| Scheme | `MT-Nord-Night.colors` | `MT-Nord-Day.colors` |
| Plasma Style | `themes/mt-nord-night/` | `themes/mt-nord-day/` |
| Look-and-Feel | `themes/mt-nord-night-global/` | `themes/mt-nord-day-global/` |
| LAF id | `com.mayanktaker.mt-nord-night.desktop` | `com.mayanktaker.mt-nord-day.desktop` |
| Aurorae | `themes/aurorae/MTNordNight/` | `themes/aurorae/MTNordDay/` |

Style ids are `mt-nord-night` / `mt-nord-day`; the widget style key stays
`MTNightshift` for all four variants. Every package ships at **1.6.0**, matching the
shared-version invariant. The plugin version is unchanged.

### Palette mapping (computed first pass; the audit is the source of truth)

Canonical Nord: Polar Night `#2E3440 #3B4252 #434C5E #4C566A`, Snow Storm
`#D8DEE9 #E5E9F0 #ECEFF4`, Frost `#8FBCBB #88C0D0 #81A1C1 #5E81AC`, Aurora
`#BF616A #D08770 #EBCB8B #A3BE8C #B48EAD`.

| Role | Nord Night | Nord Day |
|---|---|---|
| Window / View (Base) | `#2E3440` / `#232932` | `#ECEFF4` / `#F7F9FC` |
| Window alternate / Complementary | `#353C4A` / `#232932` | `#E5E9F0` / `#F7F9FC` |
| Button / Button alternate | `#3B4252` / `#434C5E` | `#E5E9F0` / `#D8DEE9` |
| Header active / alternate | `#3B4252` / `#2E3440` | `#E5E9F0` / `#D8DEE9` |
| Header inactive / alternate | `#2E3440` / `#3B4252` | `#D8DEE9` / `#E5E9F0` |
| Tooltip / alternate | `#3B4252` / `#434C5E` | `#F7F9FC` / `#E5E9F0` |
| Selection / alternate | `#84A5C6` / `#5E81AC` | `#4C6B91` / `#5E81AC` |
| Text / inactive text | `#ECEFF4` / `#D8DEE9` | `#2E3440` / `#4C566A` |

Accents and semantics: focus `#88C0D0` night and `#4C6B91` day; hover `#84A5C6`
night and `#5E81AC` day (focus reads stronger in both). Plain nord9 is 4.64:1 on the
dark Window, just under the floor, hence the lifted `#84A5C6`; plain nord10 against
white text is 4.03:1, hence the dark-on-light selection pill in Nord Night. Semantic
tones: negative `#E0848E` / `#A04752`, neutral `#EBCB8B` / `#7A5A0E`, positive
`#A3BE8C` / `#2F6B45`, link from the focus tone, visited `#BC97B5` / `#7A4F96`.

The non-canonical tones above are documented derivations (canonical Nord stepped or
lifted to clear the floors), not new palette identities. Adjust only values the audit
rejects, and record final measurements in `validation.md`.

### Generator fixes (approved for all four variants)

- `build-decoration.py` extends each variant palette with an explicit `frame_line`
  token (dark-toned for both night variants, light-toned for both day variants) so the
  frame is a subtle outline relative to that variant's header, rather than a single
  Nightshift-derived value baked at import. Regenerate all four `decoration.svg` files;
  update the frame-line description in `design.md` §12.2.
- Aurorae button SVGs (`close`, `minimize`, `maximize`, `restore`, `menu`) are generated
  from the same variant palette: icon and state colours come from the variant's text /
  selection / negative tones, geometry unchanged. Their drift check is wired into
  `make check` alongside `decoration.svg`. This fixes Dayshift's night-toned icons and
  prevents Nord Day from shipping the same defect.

### Files to touch

- `color-schemes/MT-Nord-Night.colors`, `color-schemes/MT-Nord-Day.colors` — new.
- `themes/mt-nord-night/`, `themes/mt-nord-day/` — metadata and palette copies; shared
  geometry SVGs copied verbatim.
- `themes/mt-nord-night-global/`, `themes/mt-nord-day-global/` — metadata, defaults
  (frameContrast 0.05, widget style `MTNightshift`) and palette copies.
- `themes/aurorae/MTNordNight/`, `themes/aurorae/MTNordDay/` — generated decoration
  and button SVGs, plus the geometry-only `.rc`.
- `tools/decoration-probe/build-decoration.py` — four variant palettes, per-variant
  frame line, generated buttons, drift checks.
- `tools/theme-audit/check-theme.py` — four variant entries, single 1.6.0 invariant.
- `tools/style-probe/check-style.py` — per-variant reference Window tone and pill-text
  polarity; `Makefile` grows the probe to four renders.
- `Makefile` — a variant table driving install/apply/verify-live, with `make apply`,
  `make apply-dayshift` kept as aliases and `make apply-nord-night` /
  `make apply-nord-day` added (`make apply VARIANT=nord-day` also works).
- `README.md`, `design.md`, `validation.md`, `AGENTS.md`, `PLAN.md` — pointers, final
  measurements and the new work items.

### Verification

`make check` (all four variants, four style renders), `make check-dpr2`, then live
`make verify-live VARIANT=nord-night` and `VARIANT=nord-day`, applying each in turn and
restoring the previously active theme. Review window edges on a light wallpaper as well
as a dark one, per the existing rule.
